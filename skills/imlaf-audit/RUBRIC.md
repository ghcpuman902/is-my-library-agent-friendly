# Rubric

Score each row `pass` / `warn` / `fail` / `n/a` / `blocked` for a surface
the target actually has. `n/a` means the surface doesn't exist for this
target; `blocked` means it exists but you couldn't run the check this time
and are saying so instead of guessing (see `SKILL.md` Step 5). Cite a file,
export, command, or error for every score. The "why" column is the failure
mode the criterion prevents; use it to judge severity, not just to fill in
a checkbox.

## Cross-cutting (applies across core, api, cli, ui)

| # | Criterion | Why it matters | How to test |
| --- | --- | --- | --- |
| 1 | One mental model everywhere | If the browser build and the Node/server build use different concepts, an agent has to learn two APIs for one library and will mix them up. A platform-only feature should live in an adapter and throw a clear error elsewhere, not silently behave differently. | Read the entry points for each runtime the library targets. Do the same nouns (context, session, client, whatever it calls its handle) appear in each, with the same shape? Try calling a browser-only feature from the server build and see what happens. |
| 2 | Validation without running | An agent needs to know "will this work" before spending a turn booting an app, a browser, or a device. | Find or construct a static check (a linter, a `validate()` call, a `--dry-run` flag, a type checker). Run it against something broken and see if it catches the problem without executing the broken thing. |
| 3 | Deep modules, tiny public surface | A narrow API is easier to memorize and compose correctly than a wide one; agents that see ten ways to do one thing pick the wrong one at least as often as the right one. | Count the public entry points for the common case. Is there one obvious call, with internals (parsing, layout, caching) hidden behind it? Or does the common case require assembling four low-level pieces yourself? |
| 4 | Docs are plain text and colocated | Agents explore with a shell. If the only docs live behind a JS-rendered website with no offline export, `grep` and `cat` find nothing. | Run `grep`, `find`, or `cat` against the installed package or the repo for a real question ("how do I do X"). Does an answer surface, or do you need a browser? |
| 5 | One canonical path per task | Two ways to create the same kind of object, set state, or dispatch work increases the odds an agent invents a third, wrong way by blending them. | Look for parallel APIs doing the same job (two constructors, a callback style and a promise style with no clear default). If both exist, is one clearly marked as the escape hatch rather than a coin flip? |
| 6 | Reflection over documentation | An agent that can ask the running object "what are your fields, types, and options" needs less prose and drifts less from prose that goes stale. | Pick a live object the API returns. Does it expose its own shape (properties, a `.schema`, a capabilities object), or is that information only in a doc that could be out of date? |
| 7 | Determinism by default | If the same input can produce different output run to run, an agent's own test-and-fix loop stops working: yesterday's pass isn't evidence about today. | Run the same operation (a render, a build, a test) twice with the same input. Are the outputs byte-identical, or pixel/hash-identical for visual output? If not, is there a documented deterministic mode (a seed, a mock backend)? |
| 8 | Predictable, actionable failure | A failure buried mid-operation, or a bare stack trace with no fix, costs an agent a full debugging turn it shouldn't need. | Feed the library something it can't handle: a missing peer dependency, a malformed config, bad input. Does it fail immediately with a message that names the problem and a fix, or does it fail late, silently, or with an opaque trace? |
| 9 | No hidden global state | Ambient context (a singleton, `AsyncLocalStorage`-style implicit threading) works until it doesn't: workers, generated code, and concurrent contexts break in ways an agent can't see from the call site. | Grep for module-level mutable state, singletons, or ambient-context patterns. Is the context/handle an explicit first argument everywhere, or implicit? |
| 10 | Pay only for what you import | If importing one feature pulls in the whole library, an agent-generated app that used to be small silently grows, and CI has nothing gating it. | Build the smallest possible program (one feature) and measure its bundle/import size. Is there a CI check that would fail if that grew? Compare against the library's own stated budget if it has one. |
| 11 | Legible decision trail | A library with a durable, readable record of why it rejected an alternative (an ADR, a changeset with a "why" section, an issue-tracked decision log) is one an agent (and you) can trust wasn't designed by accident, and one whose remaining rough edges are documented rather than hidden. | Search the repo/issue tracker for architecture decision records, a decisions doc, or changelog entries that explain reasoning, not just the change. Read two or three. Does the reasoning still hold, or is it hand-waving dressed as a decision? |
| 12 | Honest test/eval trust model | Tests and evals an agent leans on as ground truth are only as good as the project is honest about what they prove. A project that distinguishes hard, ungameable gates from soft/observed signals, and says what a green result does *not* prove, is safer for an agent to trust than one that reports everything as pass/fail. | Look at the test suite or any eval harness. Does it separate deterministic gates from soft/judged signals? Does any doc admit a known way to pass without actually working (a forged artifact, a stale cache)? |

## `core` (parser, schema, or domain logic shared by the higher layers)

| # | Criterion | Why it matters | How to test |
| --- | --- | --- | --- |
| 13 | Composes with the host language, not a new dialect | A bespoke DSL or file format an agent hasn't seen before costs it a whole extra thing to learn; reusing the host language's own import/export syntax (or an existing well-known standard) costs nothing extra. | Look at how the core layer's file format handles modularity (imports, composition, references). Does it borrow syntax the agent already knows, or invent new syntax? If invented, is there a stated reason (owning diagnostics, avoiding an upstream dependency) or was it invented by default? |
| 14 | Expensive parsing/analysis is opt-in | A parser, type-checker, or analyzer that rides along in every build even when unused wastes the exact budget criterion 10 protects. | Check whether the parser/analyzer is in the default import path or behind an explicit opt-in subpath/flag. Measure it. |

## `api` (the library surface a program imports and calls)

| # | Criterion | Why it matters | How to test |
| --- | --- | --- | --- |
| 15 | One native backend/runtime per class of environment in v1 | Supporting three interchangeable native backends multiplies CI, docs, and debugging surface before the API itself is proven; it's a cost paid before there's evidence it's needed. | Check how many backends/drivers exist for one environment (for example, Node). If there are several, is there a stated reason (a mature ecosystem justifies it) rather than optionality for its own sake? For a library with no native/driver layer at all (pure HTTP, pure computation), this row is a trivial `pass` and carries little signal — don't read much into it either way. |
| 16 | Honest platform gaps, no fake compatibility shims | Faking a browser-only primitive (a canvas, a DOM node) on a platform that doesn't have one creates an abstraction an agent will trust and then get burned by. | Find where the library runs on a platform missing some browser/OS primitive. Does it degrade explicitly (a documented no-op, an explicit readback API) or fake the missing piece? |
| 17 | Stable, single-versioned surface with real migration snippets | An agent applying a version bump needs copy-pasteable before/after code, not a prose paragraph it has to translate into a diff itself. | Open the changelog for the last breaking change. Does it include runnable before/after code an agent could apply mechanically? |
| 18 | No `any`/`unknown` escape hatches on the public surface | A publicly typed surface is one an agent's own type-checker can catch a mistake in before running anything; an `any` in the public API silently defeats criterion 2 for that path. | Check the public type declarations for `any`, `unknown`, or the equivalent untyped escape in other type systems. |

## `cli` (a command run in a terminal or shelled out to by an agent)

| # | Criterion | Why it matters | How to test |
| --- | --- | --- | --- |
| 19 | Ships inside the main package, one install | A second install step is a second place for an agent's plan to fail; `npx <pkg>` (or the ecosystem equivalent) should be the entire instruction. | Run the zero-argument invocation from a fresh install. Did it need anything beyond the one install command you already ran? |
| 20 | Bare invocation is the onboarding doc | The single highest-leverage thing a CLI can do for an agent is tell it, unprompted, what to do next. | Actually run the bare command (no args, no flags) and read the output. Would it get an agent unstuck with zero other context? |
| 21 | Machine-readable output by default | An agent parsing prose output will misparse it eventually; JSON by default with a human-friendly flag opt-in is the safer default. | Score data-producing commands and doc-retrieval/prose commands separately; don't average them into one verdict. Run a data-producing command (one that returns records, status, or a result) with no flags — is it JSON by default? A command whose whole job is printing prose meant to be read (`docs cat`, `help`) is fine staying prose; wrapping it in JSON would make it worse for the agent consuming it, not better. |
| 22 | Stable, specific exit codes | "Exit 1 for everything" tells an agent nothing about what kind of failure happened; distinct codes let it branch without parsing text. | Trigger two different failure kinds (bad input vs. missing dependency, for example) and diff the exit codes. |
| 23 | A health-check command that actually exercises the real thing | A static-only environment check can pass while the real operation still fails for a reason the static check didn't cover. The health check should attempt the real thing, render, connect, compile, and report the true verdict. | Run the health-check command. Does its verdict come from actually attempting the core operation, or only from checking that files/binaries exist? Break something a static check wouldn't catch and see if the verdict changes. |
| 24 | Never executes fetched code without consent and verification | An agent following an example-download or plugin-install flow should never have that flow silently run untrusted code; downloaded material should be inspectable first, and any fetch that matters should be integrity-checked. | If the CLI can fetch and use external code (examples, plugins, models), check whether it verifies integrity (checksums, pinned versions) and whether it runs the fetched code automatically or leaves that to an explicit next step. |

## `ui` (a visual or interactive component whose correctness includes "does it look right")

| # | Criterion | Why it matters | How to test |
| --- | --- | --- | --- |
| 25 | Same component works on a real backend and a deterministic mock/test path | Without a mock path, "does the UI work" can only be answered by a human looking at a screen, which an agent can't reliably do at scale. | Find the test suite for the component. Does it run against a real renderer, a mock, or both? Is the mock path exercised in CI without a display? |
| 26 | Visual correctness is a snapshot, not a prose description | A written description of what a component should look like is not something an agent (or CI) can check; a pixel/DOM snapshot is. | Look for snapshot tests (pixel diff, DOM snapshot, accessibility tree snapshot). Run one and confirm it fails when you change the visual output. If the target has no shipped widget but does have a `ui` surface (style tokens, CSS values, layout data consumed by something else), the equivalent is an exact-value assertion on that output (`toEqual` on the full computed value, not just a truthy check) that fails when any value changes. |
| 27 | No hidden singleton renderer, theme, or context unless the product is genuinely single-instance | The same failure mode as cross-cutting criterion 9, specific to UI: a hidden global theme/renderer breaks the moment an agent needs two instances (tests, multiple mounted widgets, SSR). | Try mounting or rendering two instances of the component in the same process. Does the second one work independently of the first? |
| 28 | Client-shipped bytes are a hard gate | A UI component's client bundle is the part users actually download; unlike internal tooling, going one byte over a stated budget should fail, not warn. | Find the bundle-size CI check (if one exists). Does it hard-fail on the client-shipped bundle, or only warn? If none exists, that's the finding. For a token/data-only `ui` surface with no shipped component, this collapses into criterion 10: does importing one value from this surface pull in unrelated data or code with it? |

## `mcp` (a Model Context Protocol server exposing the library as tools)

| # | Criterion | Why it matters | How to test |
| --- | --- | --- | --- |
| 29 | Tool schemas are complete enough to call blind | An agent calling an MCP tool has only the schema to go on, with no source to read. A vague or incomplete `inputSchema` (missing `required`, untyped free-form objects, one-line descriptions) forces guess-and-check calls that burn turns and can trigger side effects. | Open the tool list. For each tool, would its schema alone (name, description, `inputSchema`, `required` fields) tell you how to call it correctly on the first try? Call one with a plausible guess and see how far off you were. |
| 30 | Tool errors are structured, not a wrapped stack trace | The same failure mode as cross-cutting criterion 8, through a narrower pipe: MCP responses are the only channel back to the agent, so an error has to carry the problem and the fix in that one payload. | Call a tool with bad input or missing auth. Does the error content name the problem and a fix, or is it a generic "tool call failed" wrapping an internal exception? |
| 31 | Trust boundary is explicit: read vs. write, scoped vs. ambient | A hosted or shared MCP server that can silently take a write/destructive action, or that carries session state across unrelated callers, is a different (and worse) risk profile than one that's read-only or requires an explicit, scoped opt-in for anything that mutates. | List the tools by whether they read or write/mutate. Is every write-capable tool clearly marked, gated behind explicit confirmation or an opt-in flag, and is the server's session model documented (stateless per call, or stateful across calls)? |
